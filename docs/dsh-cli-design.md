## 1. 为什么要做

dsh 相比 openclaw 这类 agent **缺的不是「干活」，而是「被编排」**——典型例子就是**没有定时任务**。

所以方向不是「在 dsh 里补一个调度器」，而是：

- **把 dsh 变成可被另一个 agent 调用的执行体**；
- **谁来定时、跑什么、跑完汇报给谁 —— 交给 openclaw 那一侧**；
- dsh 侧只需要具备：**能被调用**（重点）、**能被查询状态**、**人能直接在 cmd 里用**（要有，但不是重点）。

一句话：**dsh 当发动机，openclaw 当调度台。**

## 2. 目标与首批验收场景

**两个方面**

1. **cmd 界面**：人能直接在终端里用 dsh —— 需要存在，**不是重点**。
2. **对外可编程调用面**：另一个 agent 能调用 dsh，形态是「各种工具」，**GET / POST 之类的接口** —— **这是重点**。

**两个验收场景**（做没做出来，用这两个场景验）

- **场景 A**：openclaw 每小时查看 dsh 的工作情况，汇报给主人。
  → 需要「查询 dsh 运行 / 工作状态」的接口。
- **场景 B**：openclaw 每 12 小时让 dsh 执行一个指定任务，且能**指定 provider、指定 model、指定 workplace**、能**新增 session**。
  → 需要「下发任务」的接口，参数要带得进去。

## 3. 先摆事实：dsh 上游已经有什么、缺什么

已经查证（都会影响方案，避免重复造轮子）：

| 已经有的 | 说明 |
|---|---|
| dsh 自带命令行（命令名就是 `dsh`） | 用「profile」切换形态：`web` / **`headless`** / `sdk` / `acp` / `base` |
| `headless` | **一次性非交互执行**：给一段指令就跑完返回，支持 stdin、JSON 事件流、指定 session、退出码 |
| SDK（Node + Python） | 程序里可以直接 `run(task)` 拿结果，底层是 stdio 协议 |
| ACP | 跨厂商的 agent-to-agent 标准协议（另一个 agent 能直接对话 dsh） |

| 确实缺的（= 我们要补的） | 影响 |
|---|---|
| **没有 MCP / 现成的「工具服务」形态** | 「另一个 agent 调 dsh」最通用的入口不存在 → **我们的重点** |
| **没有跨进程的连接/凭证文件** | 「连到已经在跑的那个 dsh」做不到，只能每次另起一个 |
| **SDK 不能中途取消、结果和调用对不上号** | 长任务的编排会难受，需要我们在外层补 |
| **没有生态运维面** | 插件 / 凭证 / profile 的日常操作都得手写命令 |

**结论**：CLI 是**依附在 dsh 上「接出来」的一层**（主人原话），**不自建 agent 逻辑**。

## 4. 我打算做的东西（草图）

### 4.1 cmd 侧（要有，非重点）

一条命令 `dx`（暂定名），常用子命令：

| 命令 | 干什么 |
|---|---|
| `dx run "任务"` | 跑一个任务，把结果打在屏幕上（可 `--json` 给脚本用） |
| `dx status` | 看 dsh 现在什么情况（在不在跑 / 有几个会话 / 最近干了什么） |
| `dx doctor` | 一条命令体检：环境、dsh 版本、插件、凭证、CLI 与 dsh 的兼容性 |
| `dx serve` | 把「对外调用面」跑起来（见 4.2） |

### 4.2 对外调用面（重点）

跑一个**本地服务**，把 dsh 的能力包装成一组「工具」给别的 agent 调（GET / POST + JSON）。
**先定工具清单，再谈实现**（主人强调的关键前置）。

草案清单（等你增删，见 §6 D1）：

| 分组 | 工具（示例） | 形态 |
|---|---|---|
| 任务 | 新建 session 跑任务 / 查任务 / 取消任务 | POST 下达、GET 查询 |
| 查询 | dsh 工作情况 / 会话列表 / 某会话的回合与工具调用 / 产出物 | GET |
| 元信息 | 可用 provider 列表、可用 model 列表、健康检查、版本与兼容状态 | GET |

### 4.3 event / hook / message（要提前设计，主人强调）

不能只有「调用—返回」，必须让调用方**在任务进行中就知道发生了什么**，并在关键节点被**通知或介入**：

- **event（事件）**：任务进行中的状态变化（开始、跑了哪个工具、产出、结束、失败）—— 调用方要能拿到；
- **hook（钩子）**：关键时刻往回调 / 通知（例如「任务完成」「需要审批」「卡住了」）；
- **message（消息）**：真正要送给人或调用方看的内容（汇报文本、错误说明）。

这三者的**边界与形态需要你拍板**（§6 D5），因为它决定整个对外协议长什么样。

### 4.4 兼容检测与告警（主人强调的重点）

dsh 本体在高速更新，CLI 依附在它上面，所以必须有**简单可靠的检测机制**：

- 把「CLI 依赖 dsh 的哪些接口 / 字段」做成一张**断言表**；
- **启动时自检 + 每次调用前轻量探测**；
- 一旦某个工具因为上游变化不好用 → **明确输出信息**：「哪个工具不可用 / 因为缺什么 / 当前 dsh 版本是什么」，而不是静默失败或抛看不懂的错；
- 两种读法都要：人看（`dx doctor` 打清楚）+ 机器看（接口返回里带 `degraded` 之类的标记）。

### 4.5 上游跟随机制（主人强调）

「dsh 更新后 CLI 如何快速跟上」要设计好：

- **契约快照**：把依赖的上游行为固化成一组可自动跑的样例（golden）；
- **自动探测**：CI 定时任务拉 dsh 最新 tag 跑快照，**一变红就告警**；
- **兼容矩阵**：CLI 版本 × dsh 版本，明确「支持到哪一版」；
- **发布**：CLI 随伞仓一起发（沿用现有全量发布），紧急修复走 patch。

## 5. 我理解的原则（不对请纠正）

1. 定时 / 调度 / 汇报对象 = **openclaw 侧**；dsh 侧只做「执行 + 查询」；
2. **不 fork、不改 dsh 本体**，子模块只读；
3. 凭证红线不变：token 之类不进仓库、不进日志、不进清单；
4. 先定**工具清单**，再定实现；先把**场景 A / B 跑通**，再谈扩展。
