# dsh-desktop 设计文档评审意见

> **状态：已被 [DESIGN.md](DESIGN.md) v1.0 取代**（2026-09 架构重构：桌面端改为纯壳，
> 不再自管 server，改为三端共享 + 委托 dsh-launcher）。以下为 v0.x 历史评审记录，仅供参考。
>
> 评审人视角：资深产品经理（PM）
> 评审对象：`docs/DESIGN.md`（草案 v0.1）
> 评审日期：2026-08-17
> 结论：**有条件通过，建议补齐下列问题后再进入 M1 开发**

---

## 0. 总评

这份设计文档整体质量较高：背景清晰、技术决策有依据（三轮需求确认 + 技术事实核实）、"零修改 dsh"的核心约束贯穿始终、风险已初步登记。

但从 PM 视角看，当前文档是**"技术方案"而非"产品设计"**。它回答清楚了"怎么做"（Electron + spawn + 双版本），但对"给谁用、怎么验证、做完算不算好"的回答偏弱。以下按优先级列出必须补、建议补、可延后三类。

---

## 1. 必须补齐（阻塞 M1 前决策）

### 1.1 缺「目标用户与使用场景」——产品定位只有"Windows 优先"没有"给谁"

文档 §1 只说"补充一个 Windows 优先的桌面端 App"，但没回答：**谁会为了用 dsh 而装一个桌面 App？**

- 如果目标用户是"不想碰命令行的普通用户"，那么 §6 的 **Slim 版定位（面向已有 Node/dsh 环境的开发者）就与产品定位冲突**——Slim 版的目标用户恰恰是"会用命令行的开发者"，他们本可以直接 `dsh web`，为什么要装 App？
- 这直接动摇双版本模型（§6）的合理性。**建议**：先定义清晰的用户画像（如：a) 轻度用户——只想要个图标双击就能聊；b) 开发者——想要托盘常驻、多开隔离、日志可视化），再倒推版本划分。

### 1.2 缺「验收/成功标准」——只有里程碑，没有量化指标

§9 的验收标准是"功能可操作、可验证"，属于功能级验收，缺少产品级成功度量。**建议至少补**：

- 冷启动到窗口可用的时长目标（M1 关键体验，spawn + 就绪判定 + 加载 Web UI 的总耗时）；
- Slim 版首启引导成功率/时长目标（涉及下载 Node，体验差距巨大）；
- 崩溃与异常退出的可恢复性目标（§1.3 明确"不做自动重启"，那么进程挂了用户看到什么？）。

### 1.3 缺「用户体验流程（首次启动 / 异常 / 升级）」的状态机

文档只描述了技术链路（§3 关键链路），没有描述**用户视角的状态流转**。以下场景必须定义清楚，否则 M2/M3 开发会反复返工：

| 场景 | 当前文档覆盖情况 | 缺口 |
|---|---|---|
| 首次启动 | 有技术链路，无 UI 文案/状态 | 端口解析失败、server 起不来时用户看到什么？ |
| server 崩溃后 | §1.3 仅"记录日志" | 窗口变白屏还是提示页？如何重启？ |
| 端口被占回退 | §7 有 | 提示方式、用户是否可改端口未定义 |
| 升级（自动更新） | D8 仅"electron-updater" | 升级时 server 与用户会话如何处理？数据迁移？ |
| 关闭窗口 | §7 托盘 | "最小化到托盘" vs "退出" 的用户预期未确认 |

**建议**：补一节「关键用户流程」，至少覆盖首次启动、异常恢复、升级三个流程的用户可见状态。

### 1.4 §10.2 三个开放问题未拍板，直接影响 M1 范围

- **Slim 版 dsh 缺失策略**（随包 dsh 代码 vs 全局安装）——这是 §6 模型的核心，不拍板 Slim 版无法设计；
- **数据目录默认策略**——影响设置页与迁移，宜早定；
- **镜像支持**——国内网络是硬约束，不是"可选优化"。

这三个问题标注"待评审讨论"，但**没有决策负责人和决策截止时间**。建议：为每个开放问题指定 Owner + 决策日期，避免进入 M1 后仍未决。

## 2. 建议补齐（提升完成度，可在 M1 内同步补）

### 2.1 「零修改」约束缺少**验证手段**

§5 反复强调"绝不直接修改子模块内文件"，但没有**如何检测违规**的机制。建议加一条：

- CI 中校验子模块工作区干净（`git -C deepseek-harness diff --quiet`），或锁定 submodule 指针的 hash 校验。

### 2.2 双版本模型缺少**包体积与性能预期**

§6 只定性说"大/小"，建议给出量级预估（如 Full 版预期体积、Slim 首启下载量），用于评估国内网络下首启体验，也用于决策"随包 vs 引导"。

### 2.3 端口解析依赖输出格式是 M1 阻塞风险，但缓解方案未固化

§10.3 已识别"端口解析依赖 dsh 输出格式"为 M1 阻塞，缓解是"健康探测兜底 + 锁定 commit"。**建议把"健康探测作为唯一就绪判定"而非"兜底"**——既然要健康探测，就不必再解析 stdout，减少一处脆弱依赖（除非需要展示真实端口，可通过 dsh 配置或探测后反查）。

### 2.4 安全与权限边界未明确

作为桌面 App，以下点文档未覆盖，但属 PM 必须关心的：

- dsh server 仅监听 `127.0.0.1`，**其他本机进程/网页能否访问该端口**？是否需要 token/鉴权（dsh 是否有内置鉴权，`--trusted-host` 语义）？
- Electron 窗口加载的是本地服务，**是否禁用了 `nodeIntegration`、是否限制了 preload 能力**？文档只在 §8 提到 preload，未给安全模型。
- 自动下载（§6.3）执行 `npm install -g` 与解压到用户目录，**权限与磁盘占用**是否需要用户确认。

### 2.5 里程碑缺少「时间与人力」估算

§9 有里程碑和交付物，但无时间估算与人力投入。作为 PM 视角，至少补一个粗粒度排期与关键路径（M1 的技术风险集中在 dsh 构建 + spawn 就绪判定）。

## 3. 可延后（不阻塞，记录在案即可）

- 产品名、图标、签名证书（§10.1）——已知依赖，等提供即可；
- macOS/Linux 预留——文档已明确非目标，无需展开；
- 日志导出格式、设置页细节交互——M3 再细化。

---

## 4. 一句话结论

> 技术方案清晰、约束合理、风险意识好，但**缺"给谁用"的产品定位、缺量化验收标准、缺关键用户流程状态机**；三个开放问题（§10.2）若不在 M1 前拍板，Slim 版与数据目录设计将无从落地。建议：**补用户画像 → 定开放问题 Owner → 补验收指标 → 补关键流程**，其余可随里程碑推进。
